# CLAUDE.md

This file defines how Claude Code should behave in this repository. Follow all instructions here precisely and consistently.

---

## Project overview

Full-stack application with a **TypeScript frontend** and **C# backend**. The human developer is the sole decision-maker and must understand every line of code — whether written by hand or generated by AI tooling.

---

## Core principle

**Comprehensibility over cleverness.** Every piece of code produced must be understandable to a developer reading it for the first time. Prefer straightforward, explicit implementations over terse or overly abstract ones.

---

## Before writing any code

- If the task, requirement, or approach is ambiguous in any way, **stop and ask a clarifying question**. Do not make assumptions and proceed.
- If completing a task would require touching many files, or has a wide blast radius across the codebase, **do not begin**. Instead, propose a breakdown into smaller, clearly scoped tasks and wait for approval on which to tackle first.
- If you spot an existing codebase pattern but believe there is a meaningfully better alternative, **present both options and ask which to use**. Do not silently deviate from existing patterns, and do not silently follow them if you have a relevant concern.

---

## Code style

### General
- Write code that is explicit and readable. Avoid magic, unnecessary indirection, or overly clever constructs.
- Use the established conventions of the file or module you are editing. Consistency with the surrounding code takes priority over personal style preferences.

### Comments
- Add **brief inline comments that explain *why*, not *what***. Do not describe what the code does — describe the reasoning or constraint that isn't obvious from reading it.
- Do not add file-level or section headers unless they already exist in the surrounding code.

### TypeScript (frontend)
- Use strict TypeScript. Avoid `any`; if a type is genuinely unknown, use `unknown` and narrow it explicitly.
- Prefer explicit return types on functions.
- Do not introduce new dependencies without asking first.

### C# (backend)
- Follow standard C# naming conventions (PascalCase for types and members, camelCase for locals and parameters).
- Prefer explicit types over `var` unless the type is immediately obvious from the right-hand side.
- Do not introduce new NuGet packages without asking first.

---

## Testing

- **All new code requires tests.** This is non-negotiable.
- Tests should be written in the same PR/commit as the code they cover — not deferred.
- Test behaviour, not implementation details. Tests should remain valid through reasonable internal refactors.
- If the right way to test a piece of code is unclear, ask before writing either the code or the tests.

---

## Builds, linters, and tests

- **Do not run builds, linters, or tests.** The developer runs these manually.
- If you believe a command is relevant for the developer to run after your changes, note it clearly at the end of your response — but do not execute it.

---

## Scope discipline

- Make only the changes required to complete the agreed task. Do not fix unrelated issues, refactor surrounding code, or make "while I'm here" improvements unless explicitly asked.
- If you notice something worth fixing that is out of scope, flag it as a separate suggestion after completing the task — do not fold it in silently.

---

## Communication

- After completing a task, provide a concise summary of: what changed, which files were affected, and any decisions or trade-offs worth knowing about.
- If you made no assumptions, say so briefly. If you did need to make a judgment call despite instructions to ask, explain why and flag it prominently.
